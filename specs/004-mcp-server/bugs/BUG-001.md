# Bug Report: Tool error codes guessed from message wording

**Type**: Spec gap. The design artifacts had no rule for classifying errors, so the implementation guessed.
**Severity**: Medium. No data is lost, but the assistant cannot correct a rejected request.
**Feature**: 004-mcp-server (branch `004-mcp-server`)
**Reported**: 2026-11-27 (recorded retroactively; the code fix is already in the working tree)
**Status**: Patched
**Patched**: 2026-11-27

## Description

`internal/mcpserver/errors.go` chose the tool error code for plain domain and application errors by searching the message for words:

- `"required"`, `"must"`, `"cannot"`, `"invalid"`, `"not enough"`, `"at least"`, `"exceed"`, `"unknown"` or `"duplicate"` gave `invalid_input`;
- `"not found"` gave `not_found`;
- everything else gave `internal`.

Any validation or not-found error whose wording missed those words was therefore reported as `internal`, with the generic message "internal error; see the tracker log". The assistant lost both the real reason and the field, and could not fix its request. Two cases were affected in practice:

- the store's user-caused errors, for example `player %q already has an active character in this campaign` and `player character %s is already in this encounter`;
- any validation message added in the future.

## Artifact Traceability

### spec.md

- **Affected user stories**: User Story 2 (campaign management, acceptance scenario 3), User Story 3 (encounter preparation), and User Story 4 (live combat, acceptance scenarios 3, 5 and 6). All of them rely on rejected requests that explain what was wrong.
- **Affected requirements**:
  - **FR-017**: "A failed operation MUST leave stored data unchanged and MUST return a message that says what was wrong and, where it applies, which field and which allowed range."
  - **SC-005**: "100% of invalid requests in the acceptance tests are rejected with a message that names the problem field, and leave stored data unchanged."
- **Gap identified**: the spec states the outcome but not that it must hold for every user-caused error, including messages added later. That guarantee needs a classification rule, which only the design artifacts can give.

### plan.md

- **Affected sections**: "Project Structure", `internal/mcpserver/errors.go` ("domain/app error → tool error codes"), and "Implementation Phases", P4 ("`dto.go`, `errors.go`, read tools…").
- **Impact**: the plan names the mapping file but not the mechanism. It should record that errors carry a kind (`domain.ErrInvalidInput`, `domain.ErrNotFound`) set where they arise, and that the adapter maps by kind only. Research R22 now records this.

### contracts/mcp-tools.md

- **Affected section**: "Error contract".
- **Gap**: the `invalid_input` row described domain validation errors as "plain `fmt` errors … passed through verbatim". Plain errors carry no kind, so the contract itself invited classification by wording. The row was updated together with the code (see "Recommended Fix").

### tasks.md

- **Affected tasks**: T029 (`internal/mcpserver/errors.go`, mapping errors to tool errors). The phase tasks whose tools return those errors depend on it: T044, T053, T057 and T073.
- **False completions**: none. T029 was done as written. The defect lies in what the task and the contract specified, not in skipped work, and the code is already corrected.
- **Missing tasks**: one task recording the fix (error-kind markers in domain, app and store, adapter mapping by `errors.Is`, and the guard test). It goes in Phase 10 so the task list shows the work.

## Root Cause Analysis

This was a design oversight. The domain and application layers report errors as plain `fmt.Errorf` strings: 84 sites in `internal/domain` and `internal/app`, and 31 in the store. Neither the contract nor research R5/R15 said how the adapter tells a user mistake from an internal failure. T029 therefore had nothing to classify on but the text. The analysis passes flagged the `field` problem (U2) and resolved it by making `field` optional, but did not catch that the code itself depended on wording.

## Recommended Fix

The fix is already implemented (research R22):

- **Domain**:
  - `domain.ErrInvalidInput` and `domain.ErrNotFound`;
  - `domain.InvalidInput(err)` and `domain.NotFound(err)`, which keep the message;
  - `ErrEncounterNotFound` and `ErrCampaignNotFound` wrap `ErrNotFound`;
  - unknown combatants are marked as not found.
- **Application**:
  - `invalidf` and `notFoundf` for its own checks;
  - marking inside the `prepare*` validation helpers;
  - marking of pure domain rule results (`ApplyDamage`, `Heal`, `AdvanceTurn`, resource spends), of the settings validation and of the activity limit.
- **Store**: user-caused guards and the duplicate errors are marked as invalid input.
- **Adapter**: `asToolError` maps by `errors.Is` only, and the word list is removed. Unmarked errors are reported as `internal`.
- **Tests**:
  - `internal/domain/errors_test.go`;
  - `internal/mcpserver/errors_test.go` (unmarked validation-like text gives `internal`);
  - the guard test `internal/app/errors_test.go` (17 user-caused paths must be marked).
- **Docs**: the `contracts/mcp-tools.md` error table and research R22. These were updated together with the code, before this report.
