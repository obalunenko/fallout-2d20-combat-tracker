# Fallout 2d20 Combat Tracker Constitution

## Project Identity

Fallout 2d20 Combat Tracker is a native desktop application for running Fallout 2d20 combat encounters. The project is implemented in Go as a single application with a layered architecture:

```text
cmd/fallout-tracker -> internal/ui/fyneui -> internal/app -> internal/domain
                                      \-> internal/store/sqlite -> internal/store/sqlite/dbgen
```

The runtime UI is built with Fyne, local persistence uses SQLite through `modernc.org/sqlite`, migrations are managed by Goose, and typed database access is generated by sqlc.

## Core Principles

### I. Layer Boundaries Are Mandatory

Domain rules live in `internal/domain` and must not import `internal/app`, `internal/store`, or `internal/ui`. Application orchestration lives in `internal/app` and depends on repository interfaces from `internal/app/repository_contracts.go`. SQLite-specific persistence lives in `internal/store/sqlite`. Fyne-specific UI code lives in `internal/ui/fyneui`. New code must preserve this dependency direction unless a spec explicitly amends the architecture.

### II. Domain Rules Before UI Behavior

Fallout combat behavior, validation, encounter ordering, resources, damage, healing, resistance, immunity, difficulty evaluation, and HP normalization must be expressed in domain/application code before UI wiring. UI code may collect input and display state, but it must not become the source of combat rules.

### III. SQLite Schema Evolves Through Migrations

Persistent data changes must be represented as Goose migrations in `internal/store/sqlite/migrations`. The sqlc schema in `internal/store/sqlite/sqlc/schema.sql`, query definitions in `internal/store/sqlite/sqlc/query.sql`, generated code in `internal/store/sqlite/dbgen`, and docs in `docs/db` must stay aligned with the migrated database. New combat stat dimensions should prefer dictionary/row-based tables over new wide columns.

### IV. Tests Guard Every Behavioral Change

Go tests are the project quality baseline. Domain behavior changes require focused tests in `internal/domain/*_test.go`. Application orchestration changes require tests in `internal/app/*_test.go`. Persistence or migration changes require repository/schema tests in `internal/store/sqlite/*_test.go`. UI collection, formatting, presenter, and controller behavior belongs in `internal/ui/fyneui/*_test.go` where it can be tested without a full manual run.

### V. Generated Code Is Regenerated, Not Hand-Edited

Files under `internal/store/sqlite/dbgen` are generated by sqlc and must not be manually edited. Changes to generated database access must start from migrations, `internal/store/sqlite/sqlc/schema.sql`, and `internal/store/sqlite/sqlc/query.sql`, then run the generator.

### VI. Local Desktop Operation Comes First

The application must remain a local desktop tracker. Default storage is `~/.config/fallout-tracker/tracker.db`, with `FALLOUT_TRACKER_DB_PATH` available for override and tests. Features should assume offline local play unless a future spec explicitly introduces networked behavior.

### VII. Audit Side Effects Must Not Break Combat Flow

Encounter operation logs are useful feedback, not critical state. Failure to append an audit log must be logged and counted as a non-critical side effect; it must not fail the primary combat/resource action after state has been saved.

## Project Structure Rules

- Entry point: `cmd/fallout-tracker/main.go`.
- Domain entities and rules: `internal/domain`.
- Use-case services and command structs: `internal/app`.
- Repository contracts: `internal/app/repository_contracts.go`.
- SQLite implementation: `internal/store/sqlite`.
- sqlc source files: `internal/store/sqlite/sqlc`.
- sqlc generated files: `internal/store/sqlite/dbgen`.
- Goose migrations: `internal/store/sqlite/migrations`.
- Fyne UI: `internal/ui/fyneui`.
- Database documentation: `docs/db` and `docs/db-normalization.md`.
- Build and verification commands: `Makefile`.

## Naming And Style

- Go package and file naming follows the existing lowercase/snake_case Go style, with tests named `*_test.go`.
- Public API names should be exported only when used across packages or useful for tests.
- Commit history currently follows Conventional Commit prefixes such as `feat:`, `fix:`, `refactor:`, `ci:`, and `build(deps):`; future branches and commits should preserve that style where practical.
- Keep generated, build, and local database artifacts out of source control (`tools/bin/`, `bin/`, `dist/`, `tracker.db` are already ignored).
- Do not store secrets or personal credentials in `.agents/`; it is used here for checked-in Spec Kit skills and project agent guidance.

## Quality Gates

Before completing a spec implementation, run the narrowest useful verification and record the result in the final response. Default gates are:

```bash
go test ./...
go vet ./...
make lint
make build
```

For database changes, also run:

```bash
make sqlc-generate
make db-doc-generate
go test ./...
```

For release workflow changes, run:

```bash
make goreleaser-check
```

## Governance

This constitution overrides generic Spec Kit template guidance for this repository. New specs must include a Constitution Check that names affected layers, persistence impact, tests, and generation steps. Amendments require a short rationale in the changing spec/plan and an update to this file. Brownfield migrated specs must be marked `status: migrated` and should document discovered gaps honestly rather than inventing behavior.
